# Отчёт

Собраны два приложения на C# / .NET 10: консольный агент LangChain и Minimal API учёта физических лиц. Модель по умолчанию — локальная Ollama `qwen3.5:4b` на `http://localhost:11434`, без ключа. Проверка `dotnet build` и `dotnet test` проходит без Ollama. Минимальный уровень логов — `Debug`; `Trace` не используется. Логи консоли идут в stderr.

## Что сделано

Консоль принимает фразу аргументом или спрашивает её при старте, отсекает текст короче 3 и длиннее 500 символов и передаёт остальное в `Chain.ReActAgentExecutor` (пакет LangChain 0.17.1). Агент выбирает один из четырёх tool. Tool проверяет JSON-аргументы и сам делает HTTP-вызов в API. API хранит физлиц в памяти процесса и публикует Swagger. Ответ человеку собирается из результата tool в четырёх строках, без сырого JSON.

Вызов HTTP внутри tool, а не отдельным диспетчером консоли, — решение из `Plan.Step1.md`. Так выполняется критерий преподавателя «tool делает реальный HTTP-вызов», а контракт автора `{ "name", "args" }` остаётся внутри tool и в логе. Свободный JSON с произвольным именем или URL не исполняется.

## Архитектура и диаграмма

Текст потока:

1. Пользователь пишет фразу в консоль.
2. Консоль проверяет длину. До модели доходит только текст от 3 до 500 символов. Пустой и более короткий ввод получают сообщение «Укажите текст от 3 до 500 символов».
3. LangChain ReAct-агент читает `Prompts/system.prompt` и выбирает tool.
4. Tool логирует контракт `{"name":"...","args":{...}}`, валидирует поля и вызывает только свой метод API.
5. Minimal API читает или меняет потокобезопасное хранилище и возвращает JSON со статусом `201`, `200`, `400` или `404`.
6. Tool логирует HTTP-статус и короткое наблюдение для модели.
7. Если запрос составной, агент может вызвать следующий tool, пока не исчерпан `Agent:MaxActions`.
8. `ResponseFormatter` печатает четыре строки. Успех ставится только если каждый вызванный tool успешен.

Это тот же путь, что на диаграмме в `Plan.Step1.md` и в `README.md`: Пользователь → ConsoleApp → LangChainAgent → PersonApiTool → MinimalAPI → InMemoryStore и обратно к человеку. Отличие от ранней формулировки в `Prompts/1.prompt` только в том, кто именно делает HTTP: не консоль после разбора свободного JSON, а сам LangChain tool. Консоль по-прежнему показывает итог по статусу и не печатает сырой JSON.

## Сценарии

Пять сценариев ниже выполнены **тестовым двойником модели**, а не живой Ollama и не другой настоящей LLM. Двойник — `FakeChatClient` в `tests/PersonAgent.Tests/FakeChatClient.cs`: он отдаёт заранее записанный текст ReAct. HTTP при этом настоящий: tool ходит в тестовый сервер API (`WebApplicationFactory`). Так проверяется путь агент → tool → HTTP без демона Ollama. Код сценариев: `tests/PersonAgent.Tests/AgentScenarioTests.cs`.

Живой прогон этих сценариев на Ollama в отчёт не входил. Его добавляет владелец в разделе «Живая модель на Ollama — заполняет владелец».

### 1. Создание, реальный HTTP

Запрос: «Создай физлицо Иванов Иван».

Ожидаемый метод: `CreatePerson`.

Ответ:

```text
Status: success
Action: CreatePerson
Data: Готово. Физлицо создано. Идентификатор: 1.
Errors: нет
```

Идентификатор зависит от уже созданных записей. В API после вызова есть физлицо с фамилией Иванов. Фрагмент лога:

```text
Контракт инструмента: {"name":"CreatePerson","args":{"firstName":"***","lastName":"***"}}
HTTP POST persons для CreatePerson
HTTP ответ CreatePerson: 201
Результат инструмента CreatePerson: HTTP 201, успех да
```

### 2. Получение, реальный HTTP

Запрос: «Покажи физлицо {id}» после создания Смирнова Петра.

Ожидаемый метод: `GetPerson`.

```text
Status: success
Action: GetPerson
Data: Физлицо найдено. Идентификатор: {id}, фамилия: Смирнов, имя: Пётр.
Errors: нет
```

```text
HTTP GET persons/{id} для GetPerson
```

### 3. Изменение, реальный HTTP

Запрос: «Измени фамилию физлица {id} на Соколов».

Ожидаемый метод: `UpdatePerson`.

```text
Status: success
Action: UpdatePerson
Data: Готово. Данные физлица изменены
Errors: нет
```

Повторный `GET` возвращает фамилию Соколов. Фраза из ТЗ автора присутствует. Лог: `HTTP PUT persons/{id} для UpdatePerson`, `Результат инструмента UpdatePerson: HTTP 200, успех да`.

### 4. Создание и список одним запросом, два реальных HTTP

Запрос: «Создай Волкова Мария и покажи список».

Методы по порядку: `CreatePerson`, затем `ListPersons`.

```text
Status: success
Action: CreatePerson; ListPersons
Data: Готово. Физлицо создано. Идентификатор: N. Список физлиц получен. Количество: M. ...
Errors: нет
```

Оба вызова дошли до HTTP. Модель вызывалась трижды: два действия и финальный ответ.

### 5. Не хватает данных, HTTP нет

Запрос: «Создай физлицо».

```text
Status: error
Action: уточнение
Data: Укажите фамилию и имя физлица.
Errors: недостаточно данных для вызова инструмента
```

Запросов к API не было. Слова «Готово» в ответе нет.

### Дополнительно

| Проверка | Итог |
| --- | --- |
| «Удали физлицо 10» | tool не вызывается, в результате есть «не поддерживается» |
| Action `DeletePerson` | `Status: error`, действие «неизвестный инструмент», HTTP нет |
| В аргументах `url` | отказ до HTTP, текст про endpoint |
| `CreatePerson` с `{}` | отказ «укажите фамилию», HTTP нет |
| `GetPerson` id `999999` | реальный `404`, «Физлицо не найдено», без «Готово», даже если модель написала про успех |
| API на закрытом порту | «API недоступен», без «Готово» |
| Тело `200` не является JSON | «API вернуло некорректный JSON» |
| 501 символ, пустая строка и 1–2 символа | модель не вызывается, для короткого текста сообщение «Укажите текст от 3 до 500 символов» |
| Ровно 500 символов | модель вызывается |
| Модель сама пишет «Готово. Данные физлица изменены» без tool | ответ заменяется на ошибку «инструмент не был вызван» |
| Ollama на `127.0.0.1:9` | «Ollama недоступен» |
| Путь `http://evil...`, `//host`, `persons/../admin` | `PersonApiClient.IsAllowedPath` возвращает false |

Отдельный прогон Kestrel, не только тестовый сервер: `POST/GET/PUT/GET /persons` на `http://127.0.0.1:5080` вернули `201/200/200/200`, неизвестный id — JSON `404`, пустое тело создания — JSON `400` с «Укажите фамилию». `GET /swagger` и `GET /swagger/v1/swagger.json` вернули `200`. Страницы Swagger в браузере не кликались: проверялся HTTP-ответ UI и JSON-описание.

## Зависимости вместо requirements.txt

Задание преподавателя говорит про `requirements.txt` или `pyproject.toml`. Проект на C#, поэтому список версий — `Directory.Packages.props`, а полное дерево — `packages.lock.json`. Команда запуска — `dotnet run`, не `python main.py`. Таблица соответствия — в `requirements.md`.

Агент не заменён другим фреймворком. Используется LangChain 0.17.1, метод `LangChain.Chains.Chain.ReActAgentExecutor` и базовый `AgentTool`. Пакет `Ollama` 1.15, который идёт вместе с LangChain, не реализует `Microsoft.Extensions.AI.IChatClient` (так записано в исходниках LangChain на теге v0.17.1). Поэтому рядом лежит короткий `OllamaChatClient`: он только доставляет текст в `POST {OLLAMA_BASE_URL}/api/chat` и возвращает ответ в тот интерфейс, которого ждёт LangChain. Выбор tool, цикл Observation и разбор Action остаётся библиотечным.

Context7 для сверки документации в этой среде потребовал отдельный вход, поэтому версии сверены по NuGet и исходникам тега `v0.17.1` репозитория tryAGI/LangChain.

## Opt-in тест живой модели

Cursor Composer из этого окружения как постоянный OpenAI-совместимый URL с ключом не доступен, поэтому теста «прямо в Composer» нет. Есть тест `LiveModel_CreatePerson_WhenConfigured`. Он запускается, только если заданы `LLM_INTEGRATION_BASE_URL` и `LLM_INTEGRATION_MODEL`, и ходит в `/v1/chat/completions`. Туда можно подставить Ollama (`http://localhost:11434/v1`), LM Studio или другой совместимый шлюз. Без переменных тест пропускается, и `dotnet test` остаётся зелёным. В последнем прогоне он был пропущен.

Тот же режим можно включить у консоли: `LLM_PROVIDER=OpenAICompatible` плюс `LLM_BASE_URL` и `LLM_MODEL`.

## Как это читалось и что сознательно сужено

- ТЗ автора описывает, что консоль сама разбирает JSON агента и вызывает API. ТЗ преподавателя требует HTTP внутри tool. В плане выбран второй вариант. Оба ограничения сохранены: набор методов фиксирован, консоль не выбирает метод сама, человек не видит сырой JSON.
- Итоговые метки совпадают с контрактом преподавателя: `Status`, `Action`, `Data`, `Errors` (`Prompts/system.prompt:40-43`, `ResponseFormatter.cs:112-115`). Текст внутри полей остаётся на русском. Значения статуса — `success` и `error`.
- Уточнение и отказ — это `Status: error`, потому что действие не выполнено. Это не сбой транспорта.
- Обновление частичное. Хотя бы одно поле кроме id. Очистить отчество или дату рождения в null нельзя.
- В лог не пишутся фамилия и имя. В ответе человеку они есть, потому что он сам их запросил.
- Хранилище не переживает перезапуск API.
- Живой прогон на Ollama остаётся за владельцем: в этой среде её нет. Сценарии 1–5 сняты с тестового двойника `FakeChatClient`. Код клиента, opt-in тест и пустой раздел «Живая модель на Ollama — заполняет владелец» оставлены для её результатов. Модель по умолчанию в конфигурации — `qwen3.5:4b`.
